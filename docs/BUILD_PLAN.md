| 10 | Knowledge base | It is a working RAG plus structured database that the agents query; ITU requires this, not a reference list. |

## 2. Architecture

### 2.1 Runtime flow (one incident)
```
Emulated Chennai network (orca/sim)
  towers · links · gateways · GNSS · signalling · power · mgmt VPN · attacker
        │ publish to MQTT
        ▼
MQTT broker (Mosquitto) ──► Collector + PP (pseudonymise)  [Y.3172 SRC → C → PP]
        ▼
M1 anomaly · M2 minutes-to-failure + exposure · M3 8-class fault/attack (+SHAP) · M4 capacity
        │ alerts/ml
        ▼
Agents (Qwen3.8) ──RAG──► ChromaDB → KB record ids
        ▼
Rule engine (P node) → verdict + KB id (or POTENTIAL_GAP + gap id)
        ▼
Commander console: plan, evidence, deadlines, clone-test result → human approval (hashed, time-limited)
        ▼
Owner agent → execute_playbook → staged rollout 5 → 25 → 100 % → auto-rollback → re-attack check
        ▼
Hash-chained audit log · drafted CERT-In / DoT notices · gap register · readiness.json
```

### 2.2 MQTT topics
| Topic | Publisher | Content |
|---|---|---|
| `telemetry/link/<site>` | simulator | link KPIs every 10 s |
| `telemetry/gnss/<site>` | simulator | GNSS receiver state every 10 s |
| `telemetry/power/<site>` | simulator | grid, battery, genset every 1 min |
| `telemetry/weather/<zone>` | simulator | rain, wind, flood every 1 min |
| `logs/mgmt/<gateway>` | simulator | management-plane sessions and commands |
| `logs/signalling/<node>` | simulator | SS7/Diameter message batches |
| `alerts/ml` | models | M1–M4 outputs |
| `actions/approved` | console | approved plan + approval hash |
| `actions/result/<owner>` | owner agent | rollout progress, rollback, re-attack result |

The audit logger subscribes to everything. Training data is written directly to Parquet; MQTT is
only used for the live demo.

### 2.3 Knowledge base (two layers over the same official sources)
- **Layer A, structured records** (`kb/india`, `kb/global`, `kb/gaps`): clause, verbatim quote,
  page, authority, binding status, in-force date, deadline, trigger. The **rule engine** reads
  this deterministically; it never uses RAG.
- **Layer B, vector index** (ChromaDB, nomic-embed-text, 256-token chunks): records plus PDF text.
  The **agents** query it; results carry record ids, and agents may only cite ids that exist in
  Layer A. Refuse below similarity 0.25 and log every tool call (same pattern as ITU's reference
  agent).
- Country swap (demo scenario 3): load `kb/global` instead of `kb/india`. Key contrast: **NIS2
  Art. 23(2)** obliges entities to warn the recipients of their services; India has no such duty
  (GAP-IN-02).

### 2.4 Response loop (agents with human approval)
1. **Monitor:** agents read alerts, config drift and advisories.
2. **Propose:** the owner agent selects a playbook from the fixed catalogue and explains it with
   KB citations.
3. **Check:** the rule engine says whether the action is compliant and which clocks start.
4. **Test:** the playbook runs in a cloned network first.
5. **Ask:** the plan is shown on the console; a human approves or rejects. The approval is a hash
   of the exact playbook, targets and parameters, with an expiry time.
6. **Execute:** the agent calls `execute_playbook(playbook_id, target, approval_token)`. The tool
   refuses if the hash doesn't match, the approval has expired, the agent doesn't own the target,
   the clone test failed or the verdict was VIOLATION.
7. **Verify:** the attack is replayed in the clone and must fail; monitoring is raised while
   terminals reconnect.
8. **Record:** audit entry, drafted notices, gap records.

Agents cannot run free-form commands, change a plan after approval, touch another
organisation's assets or reuse an approval.

### 2.5 Playbook catalogue (`playbooks/*.yaml`)
| ID | Action | Owner |
|---|---|---|
| PB-01 | Disable exposed VPN account, rotate credentials | Satellite operator |
| PB-02 | Enforce MFA on management access | Satellite operator |
| PB-03 | Block attacker sources at the management firewall | Satellite operator |
| PB-04 | Roll terminals back to last signed firmware | Satellite operator |
| PB-05 | Isolate the management segment (keep logs: CERT-In Direction (iv)) | Satellite operator |
| PB-06 | Fail over to a backup path verified clean first | Mobile operator |
| PB-07 | Re-authenticate terminals and towers | Mobile operator |
| PB-08 | Apply the vendor patch from the simulated advisory | Asset owner |
| PB-09 | Shed non-critical load to protect the battery | Mobile operator |

Each playbook defines preconditions, owner, risk, emulated steps, verification checks, rollback
steps and the KB records it touches.

## 3. Models

| Model | Question | Algorithm | Trained on | Output |
|---|---|---|---|---|
| **M1** | Is anything unusual happening? | Isolation Forest + window features (rolling SNR slope, logins/hour, commands/session, new source, off-hours); ECOD as comparison (PyOD) | normal synthetic telemetry | anomaly score; catches unknown attacks |
| **M2 minute tier** | How many minutes until this link fails, and who goes blind? | physics margin model (P.838/P.530/P.618 expected fade vs fade margin, storm-cell distance and speed) + LightGBM quantile + conformal calibration (MAPIE) | synthetic 10 s Chennai data | minutes_to_failure P10/P50/P90, exposure set, pending patches, recommended pre-emptive playbook |
| **M2 daily tier** | Which links are at risk this week? | LightGBM quantile | **real Turkcell data** (daily) | failure risk for 1–5 days |
| **M3** | Fault or attack, and which kind? | LightGBM + fade residual + SHAP + calibrated abstain | Turkcell faults + synthetic attacks | 8 classes + confidence + explanation |
| **M4** | Who gets scarce backup capacity? | Mixed-integer linear program (SciPy/OR-Tools); greedy list as fallback | no training | allocation: 112 → hospital → water → payments → rest |

Why Isolation Forest for M1: it needs no labels, so it catches attacks M3 was never trained on;
attacks are rare; it is fast and explainable. It only triggers M3 and the agents; it never acts
alone.

A failure that M2 did **not** expect, in clear weather, raises M3's attack score.

## 4. Synthetic dataset

Spec: `data/DATA_CARD.md` (v0 draft; v1 to be written). Research inputs: `data/research/01–03`
(Codex, gpt-6-luna), checked in `data/research/VERIFIED.md`.

### 4.1 Principles
- **Physics first:** ITU-R P.838-3 rain attenuation (from `data/itu_p838_3_coefficients.csv`,
  extracted from the official PDF, never hand-typed), P.530 and P.618 path methods; jamming is a
  rise in the noise floor with steady received power (SINR = S / (N + J)); battery discharge;
  GNSS sun-outage and scintillation.
- **Calibrated against real data:** Turkcell for link and fault behaviour.
- **Assumed values stated as assumptions:** traffic counts, site counts, dependence on satellite.
- Exact ground-truth labels, randomised parameters, fixed seeds; **held-out test ranges harder
  than training**.

### 4.2 Turkcell (checked from the archive)
`rl-kpis.tsv`: 1,992,986 **daily** rows, 2018-12-31 to 2020-12-25, 3,465 links, 1,674 sites,
`rlf` 0.061 % (1,219 positives); columns type, datetime, tip, mlid, mw_connection_no, site_id,
card_type, adaptive_modulation, freq_band (f1–f5), severaly_error_second, error_second,
unavail_second, avail_time, bbe, rxlevmax, capacity, modulation, rlf. `met-real.tsv`: hourly
weather from 20 stations in Turkey (contains sensor errors). Use it for daily risk and fault
calibration only, not for 10 s telemetry or Chennai climate.

### 4.3 Tables (v1 to include)
sites/topology · link telemetry (10 s) · weather (1 min, with storm cells and flood lag) · power
(grid → battery → genset, solar option) · services and traffic (112, card, ATM, events) ·
management-plane logs (with MFA result, change-ticket id, per-target result) · satellite gateway ·
**GNSS receiver** (fix, C/N0, AGC, clock offset, integrity) · **signalling** (message type, rate,
source network category, result codes, location-query rate) · **exposure** (patch state,
last_seen, monitoring status, reconnection auth events) · **minute-tier fields** (fade margin,
margin remaining, rx slope, storm distance/speed/heading, minutes_to_failure label) · labels with
provenance and attack stage.

### 4.4 Chennai scenarios
| ID | Scenario | Tests |
|---|---|---|
| U1 | Deepavali evening: payments go dark (management-plane wipe, KA-SAT pattern) | M1 early login alarm; CERT-In 6 h from noticing vs DoT 6 h from occurrence |
| U2 | Monsoon: Velachery floods, fibre cut, failover, rain fade vs jamming | fade residual; M2 countdown |
| U3 | Festival surge vs denial of service | M1 must not flag a legitimate peak |
| U4 | Cricket at Chepauk: temporary cells, crowd load | M4 keeps 112 first |
| U5 | Jammed microwave forces failover onto a trap path | PB-06 backup-path check |
| U6 | Gateway power failure drops hundreds of sites | looks like an attack, is a fault |
| + | GNSS timing spoof vs scintillation; SS7 location tracking vs roaming surge | new M3 classes |
| + | H1–H4 healing and C0–C3 coordination scenarios from the report | |

### 4.5 Validation
Distribution tests (KS, Wasserstein) against Turkcell; train-on-synthetic-test-on-real for the
fault classes; a classifier that tries to tell synthetic from real (domain gap); splits by time,
site and event to avoid leakage.

## 5. Build flow

### Done
- Repo skeleton `orca-ntn/` (MIT, docker-compose, SAMAAM layout), git initialised, no commit yet.
- Knowledge base v1: 23 records (17 quotes checked against official PDFs), 7 gaps, 8 of 12
  sources hashed. `python tools/validate_kb.py` and `pytest` pass.
- Research reports 01–03, checked; P.838 table extracted; Turkcell downloaded and profiled.
- Report, README and HTML carry the two technical figures, Qwen3.8 and LightGBM.

### Stage 1: foundations
1. Data card v1 (including the MQTT topics above).
2. Rule engine: `rules/india.yaml` + `orca/rules.py`, six verdicts, unit tests.
3. Hash-chained audit log.
4. Playbooks PB-01 to PB-09 and the `execute_playbook` tool with its four checks.
5. Checkpoint: `run_demo.py --scenario C0` runs a scripted KA-SAT timeline end to end.

### Stage 2: synthetic world
6. Generator `orca/sim/` from the data card (topology, physics, storm cells, all scenarios, exact
   labels, train/held-out ranges, seeds).
7. Validation against Turkcell.
8. Live mode: the same generator streams to MQTT.

### Stage 3: models
M1, M2 (minute + daily), M3 (8 classes), M4 (MILP), as in section 3.

### Stage 4: agents and knowledge
9. `tools/build_index.py` → ChromaDB.
10. LLM client (Qwen3.8 on Google Cloud, local fallback).
11. Six role agents with tools `query_kb`, `run_rule_engine`, `select_playbook`, `draft_notice`,
    `execute_playbook`.

### Stage 5: response loop
12. Remediation: clone test → approval → agent execution → rollout → rollback → re-attack check.
13. FastAPI commander console (alerts, M2 countdowns, verdicts, deadline clocks, approve button).
14. Runs: every scenario with the rule engine on and off; LLM citation evaluation (20–30
    questions); charts; `readiness.json`.

### Stage 6: stretch (only if 1–14 are done)
15. QLoRA fine-tune of Qwen3.8 on Colab A100; base vs fine-tuned results.
16. TabPFN comparison for M3.

### Stage 7: submission
17. Documents: Chennai story; GNSS/SS7; minute-level M2; 8 classes; M4 as MILP; "the owner's
    agent executes with a hashed human approval"; real results.
18. Colab notebook in ITU's `Sandbox_Training` format.
19. 5–7 minute video with subtitles.
20. Push to GitHub; submit by email on 10 Nov.

Stages 3 and 4 can run in parallel once Stage 2's data exists.
